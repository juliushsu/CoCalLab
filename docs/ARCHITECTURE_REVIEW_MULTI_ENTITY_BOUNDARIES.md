# CTO Architecture Review: Multi-Entity Boundaries and Duplicate Prevention

Last updated: 2026-05-08

Scope: CoCalLab backend schema/RLS/services, frontend contract, and Readdy admin flows.

## Executive Summary

CoCalLab currently uses `organizations` as the single top-level boundary for SaaS tenancy, membership, subscription, legal identity, projects, formal data, reports, factors, adjustments, and audit logs. This is workable for a single-company closed beta, but it is not safe for multi-legal-entity inventory, group consolidation, consultant workspaces, or shared emission-source accounting.

The main architectural correction is to split the current overloaded `organizations` concept into:

1. `workspaces`: SaaS tenant, billing, members, invitations, plan limits.
2. `legal_entities`: carbon-reporting legal subjects under a workspace.
3. `sites/facilities`: physical locations under legal entities.
4. `emission_sources/equipment/processes`: accountable physical/process assets.
5. `report_boundaries`: immutable boundary snapshots per project/report.
6. `entity_relationships`: parent/subsidiary/affiliate/supplier/customer graph.
7. `emission_source_ownerships`: allocation/control/equity rules by legal entity and period.

Closed beta should not open unrestricted organization creation as currently modeled. It should either rename the current `organization` UI to `workspace` and introduce a minimum `legal_entity` table, or temporarily constrain each workspace to exactly one legal entity with explicit copy and UI labels.

## B. 主要風險

1. 多法人不可表達

One workspace cannot own many legal reporting subjects. Users will create multiple `organizations`, splitting subscription, membership, documents, and reports across unrelated tenants.

2. 據點無法獨立

No first-class `site/facility` table is present in the committed schema. Activities cannot be scoped to a plant, branch, warehouse, office, or production line.

3. 邊界污染

`projects.boundary_type` is a text label, not a boundary engine. It does not define which entities, sites, sources, or ownership ratios are included.

4. 同一排放源重複計算

There is no global or workspace-level emission source identity, no ownership table, and no allocation lock. Two legal entities can enter the same equipment or bill independently.

5. 顧問帳號跨客戶資料風險

Consultants need one workspace with multiple client legal entities, or multiple workspaces with scoped access. Current `organization_members` grants access to everything under that organization. There is no client/entity-level role scope.

6. 報告主體與帳號租戶混淆

`report_generations.organization_id` is both account tenant and reporting subject. A group report needs one workspace and many legal entities; current schema cannot represent this cleanly.

7. RLS 無法精準隔離 legal entity

RLS is correct for single-tenant isolation but not for multi-entity isolation within a tenant. Legal entity permissions, site permissions, and consultant client scopes need their own policy layer.

8. Adjustments / certificates may be over-applied

Adjustment items target only `organization` or `project`, and report generation pulls organization-level approved adjustments for project reports. Without entity/source allocation, certificates can be applied to the wrong boundary or reused across boundaries.

## C. Canonical Model Proposal

### C1. `workspaces`

Purpose: SaaS tenant, billing, subscription, members, invitations, plan limits.

Recommended columns:

- `id uuid pk`
- `slug citext unique not null`
- `display_name text not null`
- `billing_customer_ref text`
- `plan_code text not null`
- `status text not null default 'active'`
- `default_country_code char(2)`
- `default_timezone text`
- `metadata jsonb not null default '{}'`
- timestamps

Migration rule:

Existing `organizations` rows should become `workspaces` first.

### C2. `legal_entities`

Purpose: legal reporting subjects.

Recommended columns:

- `id uuid pk`
- `workspace_id uuid not null references workspaces(id)`
- `entity_code text not null`
- `registered_name text not null`
- `display_name text not null`
- `tax_id text`
- `country_code char(2) not null`
- `registration_address text`
- `industry_code text`
- `status text not null default 'active'`
- timestamps

Unique:

- `(workspace_id, entity_code)`
- partial unique `(workspace_id, country_code, tax_id)` when `tax_id is not null`

Migration rule:

Create one `legal_entities` row per existing `organizations` row during Phase 1.

### C3. `sites` / `facilities`

Purpose: physical locations, plants, offices, warehouses, branches.

Recommended columns:

- `id uuid pk`
- `workspace_id uuid not null`
- `legal_entity_id uuid not null references legal_entities(id)`
- `site_code text not null`
- `site_name text not null`
- `facility_type text`
- `address text`
- `country_code char(2)`
- `timezone text`
- `geo_point geography/metadata`
- `status text not null default 'active'`
- timestamps

Unique:

- `(workspace_id, legal_entity_id, site_code)`

### C4. `emission_sources` / `equipment` / `processes`

Purpose: globally identifiable real-world emission sources.

Recommended columns:

- `id uuid pk`
- `workspace_id uuid not null`
- `site_id uuid references sites(id)`
- `source_uid text not null`
- `source_type text not null`
- `source_name text not null`
- `equipment_code text`
- `serial_number text`
- `process_code text`
- `asset_fingerprint text`
- `commissioned_on date`
- `decommissioned_on date`
- `status text not null default 'active'`
- metadata
- timestamps

Unique:

- `(workspace_id, source_uid)`
- optional unique `(workspace_id, asset_fingerprint)` where present

### C5. `report_boundaries`

Purpose: immutable boundary definition for a project/report.

Recommended columns:

- `id uuid pk`
- `workspace_id uuid not null`
- `project_id uuid references projects(id)`
- `boundary_code text not null`
- `boundary_name text not null`
- `consolidation_method text not null`
- `reporting_period_start date not null`
- `reporting_period_end date not null`
- `included_legal_entities jsonb not null`
- `included_sites jsonb not null`
- `included_emission_sources jsonb not null`
- `exclusions jsonb not null default '[]'`
- `allocation_rules_snapshot jsonb not null`
- `status text not null default 'draft'`
- timestamps

`report_generations` should store `report_boundary_id` and `boundary_snapshot`.

### C6. `entity_relationships`

Purpose: group and supply-chain graph.

Recommended columns:

- `id uuid pk`
- `workspace_id uuid not null`
- `from_legal_entity_id uuid not null`
- `to_legal_entity_id uuid not null`
- `relationship_type text not null`
- `ownership_ratio numeric(9,6)`
- `effective_from date not null`
- `effective_to date`
- `metadata jsonb`
- timestamps

Allowed `relationship_type`:

- `parent`
- `subsidiary`
- `affiliate`
- `joint_venture`
- `supplier`
- `customer`

### C7. `emission_source_ownerships`

Purpose: allocate one physical source across legal entities/boundaries.

Recommended columns:

- `id uuid pk`
- `workspace_id uuid not null`
- `emission_source_id uuid not null references emission_sources(id)`
- `legal_entity_id uuid not null references legal_entities(id)`
- `site_id uuid references sites(id)`
- `operational_control boolean not null default false`
- `financial_control boolean not null default false`
- `equity_share numeric(9,6) not null default 0`
- `allocation_ratio numeric(9,6) not null`
- `allocation_method text not null`
- `effective_from date not null`
- `effective_to date`
- `status text not null default 'active'`
- evidence fields
- timestamps

Constraints:

- `allocation_ratio between 0 and 1`
- `equity_share between 0 and 1`
- no overlapping active ownership windows for the same `(emission_source_id, legal_entity_id, allocation_method)`
- sum of `allocation_ratio` for a source/method/period should be <= 1 unless marked as non-exclusive by policy

## D. Migration / RLS / Service Proposal

### D1. Staged schema migration

Phase 1 minimal tables:

- `workspaces`
- `workspace_members`
- `legal_entities`
- `sites`

Phase 1 compatibility columns:

- Add `workspace_id` to existing `organizations`, or rename later after compatibility period.
- Add `workspace_id`, `legal_entity_id`, `site_id` to `projects`.
- Add `workspace_id`, `legal_entity_id`, `site_id` to `uploaded_documents`, `extracted_document_drafts`, `emission_activities`, `calculation_results`, `report_generations`, `ai_audit_results`, `audit_logs`, `carbon_adjustment_items`, `adjustment_certificates`, `adjustment_applications`, `adjustment_audit_logs`.

Phase 2 tables:

- `entity_relationships`
- `emission_sources`
- `processes` or process fields on emission sources
- `emission_source_ownerships`

Phase 3 tables:

- `report_boundaries`
- `boundary_emission_source_allocations`
- `group_consolidation_runs`
- `group_consolidation_results`

### D2. RLS proposal

New RLS helper:

```sql
is_active_workspace_member(target_workspace_id uuid, allowed_roles workspace_role[] default null)
```

Entity-level helper:

```sql
can_access_legal_entity(target_legal_entity_id uuid, allowed_roles workspace_role[] default null)
```

Recommended policy shape:

- Platform tenant isolation by `workspace_id`.
- Optional legal-entity row filtering by membership grants for consultant/client scenarios.
- Service-role edge functions must always validate `workspace_id + legal_entity_id + project_id` consistency.

### D3. Service proposal

Update required service contracts:

- `create-organization` becomes `create-workspace`.
- Add `create-legal-entity`.
- Add `create-site`.
- Add `create-project` with required `workspace_id`, `legal_entity_id`, and optional `site_id`.
- Add `create-report-boundary`.
- Recalculate and generate report must receive or derive `report_boundary_id`.

Important guard:

Any write with both `workspace_id` and `legal_entity_id` must assert the legal entity belongs to the workspace. Any write with `site_id` must assert the site belongs to the same legal entity/workspace.

### D4. Frontend contract proposal

Rename concepts in DTOs:

- `Organization` UI model becomes `Workspace` for tenant/members/subscription.
- Add `LegalEntityDTO`.
- Add `SiteDTO`.
- Add `EmissionSourceDTO`.
- Add `ReportBoundaryDTO`.

Compatibility:

Keep legacy `organization_id` in responses during migration, but mark as `workspace_id` alias in DTO comments until removed.

## E. Report Boundary / Consolidation Proposal

### E1. Global emission source identity

`emission_sources.source_uid` should be the canonical identity inside a workspace.

Derivation hierarchy:

1. Registered asset ID or meter ID.
2. Equipment serial number + site + process code.
3. Utility meter/customer number + address/site.
4. Supplier-provided source ID.
5. System-generated UUID with required manual duplicate review.

Also store `asset_fingerprint` from normalized fields to flag suspected duplicates.

### E2. Duplicate prevention

At activity creation:

- Link activity to `emission_source_id` when possible.
- If a new activity uses same `source_uid`/fingerprint/period as another entity, return duplicate warning.
- Require allocation or explicit exclusion before report finalization.

At calculation:

- Calculation should compute gross source-level emissions once.
- Legal entity results should be produced through allocation rows.

At report:

- Report generation should reject boundaries where one source is included more than once at total allocation > 100% for the same method/period.

### E3. Allocation ratio

Fields:

- `allocation_method`: `operational_control | financial_control | equity_share | manual_contractual | metered_split`
- `allocation_ratio`: applied to source emissions for that legal entity/boundary.
- `allocation_basis`: evidence/method note.
- `effective_from/effective_to`: period validity.

Method behavior:

- `operational_control`: controlling entity gets 100%, others 0 unless policy explicitly allows split.
- `financial_control`: financially controlling entity gets 100%.
- `equity_share`: allocation equals ownership/equity percentage.
- `manual_contractual`: uses contractual allocation with evidence.
- `metered_split`: uses measured split by meter/submeter.

### E4. Boundary snapshot

Every `report_generation` must save:

- `report_boundary_id`
- `boundary_snapshot`
- `consolidation_method`
- `legal_entity_snapshot`
- `site_snapshot`
- `emission_source_allocation_snapshot`
- `duplicate_check_snapshot`

This is required because the same source can be aggregated differently under operational control, financial control, and equity share.

### E5. Different report口徑 / different aggregation result

Do not mutate underlying activities for each report method. Instead:

- Store raw activity/calculation once.
- Store allocation/boundary snapshots per report.
- Generate aggregation results per `report_boundary_id + consolidation_method`.

This allows one dataset to generate:

- Legal entity standalone report.
- Facility report.
- Operational control group report.
- Financial control group report.
- Equity share group report.

## G. Closed Beta 前必須修的項目

P0 before opening organization creation:

- Decide and label current `organizations` as either workspace or legal entity. Do not let UI imply both.
- If keeping current schema for beta, enforce 1 workspace = 1 legal entity and label it plainly.
- Hide or gate multi-organization creation for testers unless the tester scenario explicitly needs multiple isolated tenants.

P0 before any multi-entity customer:

- Add `workspaces`, `legal_entities`, and `sites`.
- Add membership/RLS helpers by workspace.
- Add `legal_entity_id` and `site_id` to projects, documents, activities, calculation results, reports, adjustments, and audit logs.
- Add validation that `project_id`, `legal_entity_id`, `site_id`, and `workspace_id` belong to the same hierarchy.

P1 before group reporting:

- Add `entity_relationships`.
- Add `emission_sources`.
- Add `emission_source_ownerships`.
- Add duplicate detection SQL and report-generation blockers.
- Add `report_boundaries` and boundary snapshots.

P2 before enterprise consolidation:

- Add group consolidation engine.
- Add per-method aggregation result tables.
- Add boundary comparison views.
- Add consultant/client legal-entity permission scopes.

## SaaS Plan / Pricing Implications

Starter:

- 1 workspace.
- 1 legal entity.
- Limited sites.
- No group consolidation.

Growth:

- Multiple legal entities.
- Multiple sites.
- Emission source registry.
- Duplicate warnings.
- Entity/site-level reports.

Enterprise:

- Group consolidation.
- Entity relationships.
- Ownership/allocation engine.
- Operational control / financial control / equity share report variants.
- Consultant/client scoped access.
- Advanced audit and boundary snapshots.

DB enforcement:

- Store plan limits on `workspace_subscriptions.features`.
- Enforce create limits in service functions, not only frontend.
- RLS remains access control; plan limits are business rules enforced by RPC/edge functions.

## Testing / Migration Plan

Phase 1 verification SQL:

- Workspace can own many legal entities only if plan allows.
- Starter workspace cannot create second legal entity.
- Project must reference legal entity in same workspace.
- Site must reference legal entity in same workspace.
- Activity cannot reference site outside project legal entity.
- Existing one-organization seed migrates to one workspace + one legal entity.

Phase 2 verification SQL:

- Relationship graph supports parent/subsidiary/affiliate/supplier/customer.
- Ownership windows cannot overlap invalidly.
- Allocation ratios cannot exceed 100% per source/method/period.
- Shared source across legal entities requires ownership/allocation rows.

Phase 3 verification SQL:

- Same raw activity can produce different aggregation results by method.
- Operational control report includes 100% controlled sources.
- Equity share report applies ownership ratios.
- Boundary snapshot remains unchanged after entity/source edits.
- Duplicate source blocker prevents final report if allocation is missing.

## Final Recommendation

For closed beta, keep the current system stable but stop treating `organization` as a final carbon-domain abstraction. Rename or explain it as workspace in UI, add the minimum `legal_entities` and `sites` layer, and block duplicate-risk scenarios until `emission_sources`, `ownerships`, and `report_boundaries` exist.

This is the architectural hinge: once workspace/legal entity/site/source are separated, group consolidation becomes an additive engine. If they stay merged under `organizations`, every later enterprise feature will fight the data model.
