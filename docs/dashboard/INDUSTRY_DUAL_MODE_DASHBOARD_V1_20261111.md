## 1. Owner 決策與範圍

Owner 已核可「雙模式＋業態場景＋資料可追溯」，旅宿作第一個完整版本，再擴充其他業態。Owner 後續明確要求各行業類別模板不同，且指出初版動畫缺車、外觀較像 8-bit，未達期望的任天堂時代 16/32-bit 遊戲質感。

因此：
- 已核可：功能方向、旅宿先行、本規格與 GitHub 工單建立。
- 必須修正：美術豐富度、景深、材質、人物與車輛的實際動畫。
- 各行業模板必須有自己的資訊結構、布局、動線、動態角色、指標與經典表格；不能只替換同地圖的名稱和圖片。
- 美術新樣張尚未核可；生成的靜態概念圖只用於美術討論，不算可播放程式、動畫或功能證據。
- 既有商業發布 HOLD 不因本設計核可解除。雲端變更、付費資源及正式上線另依既有授權與驗收。

## 2. 產品目的與共用能力

使用者開啟首頁須能辨識：目前單位／據點／期間、排放主要來源、資料缺漏、下一步處理。客戶首頁可使用像素場景；稽核、審核及密集輸入頁面優先經典文字模式，偏好按帳號記錄。

兩模式由相同授權資料快照呈現。切換保留 org、site、period、filters、selected source；失效選取須清除並說明。切租戶須取消未完成請求、清除前一租戶資料及選取，舊回應不得覆寫新租戶。

共用：權限、期間與據點選取、資料快照、計算／分攤、來源追溯、模式切換、缺件／待審狀態、可移植渲染與動畫工具。
業態獨立：scene layout、動線網路、人物與車輛種類、動畫事件、metric mapping、action mapping、classic columns 與 drilldown。
各專案獨立資料、憑證、儲存與部署；共用程式採可移植模組。

## 3. 六套獨立模板定義

下列指標是產品候選，啟用必須由既有核准計算／分攤契約供應。缺分母或功能時顯示待補／未提供，不以示例值補足。

### HOSPITALITY：旅宿服務園區（第一個完整實作）
- 資訊主軸：住宿服務、房晚、能源與後勤。
- 布局：飯店入口及客房樓為主體，餐廳、熱水機房、花園步道、後勤補給區各有區域；車道與人行道分離。
- 主要互動：點客房／機房／餐飲區看已計算來源；點缺件看應補清單；房晚入口查看分攤基準。
- 動態：接駁巴士進場停靠、旅客汽車入場停車、補給貨車到後勤區；旅客拖行李、員工搬運。
- KPI：已計算 tCO₂e、資料完整度、房晚、每房晚排放；每筆住宿分攤依分攤引擎交付狀態啟用。
- 經典欄位：據點／來源區、活動類型、期間、憑證狀態、排放、房晚或分攤依據、追溯入口。
- 待辦：能源缺件、房晚未補、待審憑證、計算失敗。

### MANUFACTURING：生產流程工廠
- 資訊主軸：產線、批次及產量。
- 布局：原料區 → 各產線站點 → 成品區，能源設備另有側區；不套用旅館建物配置。
- 主要互動：選產線或批次看能源／活動與計算；選產量分母查來源。
- 動態：站點加工、作業員操作、搬運車在指定物流通道運輸；不沿用旅客與接駁車語意。
- KPI：已計算排放、產線／批次分布、產量、每件／每噸產品排放。
- 經典欄位：廠區、產線、批次、能源／活動、產量與單位、排放、分攤方法、來源。
- 待辦：產量未填、批次未對應、能源缺件、審核或計算失敗。

### LOGISTICS：倉儲配送網
- 資訊主軸：入庫、揀貨、裝車、運輸及貨物流。
- 布局：收貨月台、倉位與揀貨區、出貨月台構成倉內動線；對外配送以路網／站點呈現。
- 主要互動：選倉區、運輸批次／配送單查看能源與運輸活動；不將虛擬地圖距離當真實里程。
- 動態：搬運設備依通道取放、貨車停靠月台、配送車沿路網移動。
- KPI：倉儲／運輸排放、貨重、已知運距、每噸公里排放；每筆配送依核准分攤。
- 經典欄位：倉別、運輸／配送單、貨重、運距、燃料或電力、排放、分攤與來源。
- 待辦：貨重／里程未補、配送對應缺失、燃料資料缺件。

### FOOD_SERVICE：備餐供餐工作區
- 資訊主軸：備料、烹調、冷藏與用餐服務。
- 布局：廚房工作區與用餐區雙區，冷藏及能源設備為獨立來源區；不使用物流路網作主要畫面。
- 主要互動：點工作區查看能源來源；點服務人次／交易分攤查看基準。
- 動態：備餐、出餐與服務員送餐；補給車僅出現在後勤，不作主動畫。
- KPI：已計算排放、能源分布、服務人次、每人次／每筆交易分攤；食材排放依已有邊界才啟用。
- 經典欄位：門市、工作區、能源／已納入活動、人次、交易分攤依據、排放、來源。
- 待辦：人次／營運時段缺失、憑證缺件、審核待辦。

### BUILDING：樓層與分表管理
- 資訊主軸：樓層、承租單位、公設與能源分配。
- 布局：建築剖面或可展開樓層，分表及公設機房對應樓層／區域；不是平面小鎮。
- 主要互動：點樓層／分表看用能與來源；切公共／專用區查看分攤。
- 動態：電梯、設備運轉與人員巡檢；只有真實量測接入才顯示即時能流。
- KPI：能源／排放、公共區分攤、分表覆蓋、每平方公尺排放。
- 經典欄位：樓層、區域／承租戶、分表、能源、面積、分攤規則、排放、來源。
- 待辦：分表缺讀、面積／租用期間缺失、分攤待確認。

### PASSENGER_TRANSPORT：路線場站班次
- 資訊主軸：路線、班次、乘客與里程。
- 布局：站點及路線網為主要畫面，車庫／補能設施在側；地圖如僅示意須標示。
- 主要互動：選路線／班次查燃料、載客與里程；選旅程查人公里分攤。
- 動態：發車、行車、到站、回場與補能，站點停靠節奏與班次狀態對應。
- KPI：路線排放、載客量、里程、人公里及每人公里排放。
- 經典欄位：路線、班次、車輛、載客數、里程、燃料／電力、排放、分攤與來源。
- 待辦：載客／里程缺失、班次能源未對應、資料待審。

複合業態：同一組織可依據點／營運模組使用不同模板。切換模板是檢視既有業態，不賦予資料或指標權限。企業總覽依標準活動識別與彙總契約去重；同一活動不能因出現在旅宿餐廳與餐飲模板而計入兩次。

## 4. 美術與動畫的可驗收要求

目標為原創晚期 16-bit／早期 32-bit 2D 管理遊戲質感，數字代表視覺方向，不是要求使用歷史硬體或顏色限制。保留俐落像素邊緣，材質有多階明暗，建物具有屋頂、窗框、招牌、遮棚及投影，前後遮擋一致，避免粗大單色方塊和火柴人物。

美術規格：
- 先選定一致邏輯像素比例與整數縮放策略；人物建議 32–48 邏輯像素高、車輛 64–128 長，尺寸由樣板校正。
- 地景、建物、車輛、人物、標籤分層；UI 文字維持現代可讀字體。
- 旅宿須提供巴士、補給貨車、旅客汽車，各有清楚輪廓、車窗、車輪、陰影。
- 人物含至少 4 方向步行，每方向 6–8 幀；旅客行李、員工搬運可辨識。
- 車輛具行駛、轉彎／方向切換、停靠與離場，沿道路而行；人物沿步道，不穿建築或停靠車輛。
- 氛圍動畫可以循環，資料事件只在事件發生時播放；demo operation 與真實事件要可辨識。不可用虛構車流暗示即時營運或即時排放。

必交：靜態全場樣張、可播放互動樣板、至少 20 秒實錄、素材清單。靜態概念圖不能替代動畫交付。

動畫可暫停、低動態可用，遵循 prefers-reduced-motion、背景頁停動。原創場景不使用既有遊戲角色或品牌標識。

## 5. 資料與追溯契約

正式映射先由實作者固定 source_commit 後對照現有端點；本文件不創造新的已存在端點。
每個數值需綁 org/site/period、來源活動、計算版本／快照、因子版本、審核狀態、更新時間；強度及分攤另需分母與分攤方法。
追溯順序：場景來源 → 活動 → 憑證 → 計算／因子快照 → 審核紀錄。資料不存在、無權限、處理中與失敗要分別顯示。

維持 source_type/data_level 雙軸、activity_data_level/factor_data_level 分離；同活動 direct emissions 與 factor-based 結果不得重複計入，歷史 snapshot 不覆蓋。
完整度以同期間應收清單為分母，不等於審核完成率或減碳率。
缺資料不得以 0 取代；待審數值是否納入依既有契約，UI 必須說明口徑。缺基準或不可比期間不顯示減碳率。
使用相同服務與快照支援兩模式，不在動畫層另算碳排；Storage／憑證也須驗授權。
