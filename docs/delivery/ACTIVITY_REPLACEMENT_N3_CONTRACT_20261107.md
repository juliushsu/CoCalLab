# N3 最小活動取代契約（本機開發候選）

依 CTO 2026-11-07 裁定；先有本契約與案例，再實作。RELEASE HOLD；不操作雲端、不自動重算、不改寫歷史報告。本契約不是跨產品版本平台。

## 寫入與讀取

- 新的受控服務接收 organization_id、project_id、predecessor_activity_id、request_id、mode（correct / exclude）、非空 reason；correct 提供既有人工活動欄位，exclude 沿用原數量與單位，明確記錄 excluded 與排除原因。JWT 身分由服務端取得，不採用前端 actor。
- 只允許 active 單位 owner/admin/editor、可寫訂閱、同單位專案的目前有效活動。來源文件、草稿及來源屬性由服務端從前版繼承，不可由呼叫者改綁。不重新聲稱 OCR、原始轉錄或雙人覆核。
- 每次建立新的活動 ID 與一條不可由普通角色寫入的取代紀錄，包含前版、新版、操作者、理由、時間與操作識別。被取代的原活動、其原計算、原草稿、已保存報告及封存證明保持原值；不得靠修改原活動 status 或填零排除。
- 同一前版最多一個直接後繼，只可取代目前有效末端；互相競爭的取代只能一個成功。新增後繼與保存關係、稽核同一 SQL 交易完成；部分失敗全部 rollback。
- 重送須綁定 actor、範圍、前版、mode、reason 與正規化新輸入。同請求同意圖查回原新版；不同意圖拒絕。回覆遺失保留原 request_id，可核對或重送，不另建 ID。
- 後續計算與報告只採用有效末端，不能同時計入新舊。清單保留歷史可見，明示已取代及前後版本；統計、明細、匯出／報告來源與新計算使用一致有效集合，不能只在 UI 隱藏舊版。
- 未被取代的其他目前有效活動，沿用既有通用重算的 latest 旗標語意；此功能不擴建所有計算列的不可變平台。
- 取代後目前計算權威立即過期；只有新一次通用重算成功後可保存新版報告。過期判定不可藉由修改已被取代活動的歷史計算列實現。舊計算重送只能回原歷史結果，不能成為新版報告依據。

## 先行必要案例

1. 保留原活動／計算／報告／封存證明的完整 JSON，correct 新版後逐列完全相同；舊版仍可讀，新版尚無可信計算。
2. 合法 correct 100→120 kWh：重算只含120，不含220；新版報告來源映射只含新版，舊報告原封不動。
3. 合法 exclude：保留原 quantity/unit、新版明確 excluded／reason，計算及報告列為排除，不當成零用量。
4. 同 request 同意圖、回覆遺失後 lookup/retry，回原新版且 activity/ledger/audit 不增加；改 intent 或 actor 拒絕；即使後續再被取代，同原請求仍可查回該原後繼，另顯示其歷史狀態；撤權後 lookup 也拒絕。
5. 另一 request 取代已被取代前版、循環／跨租戶／viewer／readonly／撤權／偽造來源／REST 寫入關係拒絕，無新增活動、計算或稽核。
6. 在新列、關係或稽核保存失敗時 transaction rollback，原版仍唯一有效；同 ID 可安全重試。
7. 來源文件／草稿已保留時仍能建立可追溯更正版，不修改原件；已刪除或無效來源不得藉取代升格。
8. UI 明示 loading、失敗、未確認、成功及重算需求；切換單位／登出使舊回應不採用，保存中的請求保留 ID 以核對。
9. PGlite 序列衝突及故障注入是來源證據；獨立 SQL 連線競爭、鎖等待與真 Supabase／JWT／Storage 均另列 NOT_RUN，不能以 Promise.all 聲稱實測。

部署注意：既有專案須重新計算，才能產生新版報告；進行中的舊重算可能失敗。不自動重算或覆寫歷史報告。實際 migration／資源操作另需 Owner 明確授權。
